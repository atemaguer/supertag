# Rust port capability ledger

Internal contributor record for the Rust rewrite. It is not user documentation and makes no
product claim. The ledger defines when the rewrite is done: every row is either covered, a
recorded deliberate change, or dropped with approval.

**Location.** The assignment asked for `contributing/rust-port-capability-ledger.md`. In this
repository `contributing/` is gitignored (`.gitignore` line 35) and `AGENTS.md` keeps internal
design notes there, so a file there could not be committed or reviewed. The assignment's fallback
is `rust/docs/`, which is tracked. Nothing under `docs/` links here.

**Baseline.** The TypeScript product at the rewrite's merge base with upstream, `a369dc4`, which
includes the `0b6a8ff` baseline named by the approved design.

## How to read this ledger

Capabilities were derived by sweeping `tests/` (306 test files), `tests/e2e/`, `tests/runtime/`,
`packages/**/*.test.ts`, `apps/cli/*.test.ts` and `helpText()` in `apps/cli/src/index.ts`,
`apps/tui/*_test.go`, `sdks/python/tests/`, and every page under `docs/`. The progress log was
used only to find where Rust evidence lives.

Every tracked TypeScript, Go, and Python test file (`*.test.ts`, `*_test.go`,
`sdks/python/tests/test_*.py`) is cited, by path or glob, in the TypeScript tests column of a
capability row or in [Test files that are not product capabilities](#test-files-that-are-not-product-capabilities).
`tests/rust-port-baseline/capability-ledger.test.ts` enforces this, and checks that each cited Rust
test name appears in the Rust file cited before it.

Rust evidence was identified from the test function names in `rust/crates/*/tests/*.rs` and
`#[cfg(test)]` modules, and from the store, RPC, and CLI operations each test invokes. Tests marked
**(read)** were read in full while writing this ledger. The rest were checked by name and by the
operations they call, which shows what they exercise but not every assertion.

| Status | Meaning |
| --- | --- |
| **Both DBs** | A Rust test exercises the capability on SQLite and on PostgreSQL |
| **SQLite only** | Rust coverage exists, but no PostgreSQL run of that behavior exists |
| **Partial** | Some of the TypeScript behavior has Rust coverage; the gap column says what is missing |
| **Open** | No Rust implementation or no Rust test was found |
| **Changed** | Deliberately different in Rust under the approved design; the reason is given |
| **Dropped** | Removed with the user's approval; the approval is cited |
| **Proposed drop (needs approval)** | Recommended for removal under the new architecture; the reason is given and approval is pending |

Approved scope decisions cited below are from the approved design
(`rust-port-design-and-plan.md`, section 1) and the November 12 handoff: no compatibility with
old runtime, wire, API, or Worker interfaces; fresh Rust state with old data archived and no
importer; separate Gateway; Go TUI and Tauri desktop retained; TypeScript and Python keep client
SDKs and harness adapters but no longer implement full Worker runtimes.

## Prioritized open gaps

Priority reflects risk to accepted work and to the cutover, not effort.

1. **Attempt time limit and host recovery semantics** (area 5): ported. The Attempt time limit
   defaults to TypeScript's 60 minutes and a supertag.yaml host service sets it with
   `attempt-timeout-seconds`. A host restarted after a forced kill reclaims its interrupted Attempt
   automatically, as a failed Attempt with an unknown outcome, once its process record proves
   every process it started on the host is gone; otherwise, and always for Attempts that used a
   remote sandbox or shared execution (as in TypeScript), it still waits for `supertag task
   resolve-attempt`. A remote-sandbox host refuses a time limit above the providers' 3600-second
   sandbox lifetime. `supertag recover worklet` is dropped (approved by the operator on 2026-11-13). The
   Workspace `setup` command (area 9) is ported, running in each Task checkout with TypeScript's
   10-minute limit, and the requested and applied limits of the Task execution report (area 5)
   are ported; the report's threshold and cleanup classifications are not.

   G1 (two contracts failing on both databases) is fixed: `31232dc` removed their stale
   downgrade simulations, and both pass on SQLite and PostgreSQL at `4d3e7f7`. The flaky
   `supertag-worker-host --lib` journal tests are fixed: the state-directory `flock` stayed held
   by children spawned concurrently on other threads until their exec, and is now released
   explicitly on drop (area 5). The same release now covers the Workspace and source preparation
   locks on the Worker Host's Task path. Other plain `try_lock` sites outside the Worker Host
   (`shared-execution`, the Gateway delivery journal, and `cli` local state) are unchanged.
2. **Hard-crash durability.** Covered by `crash_durability.rs` and the durable PostgreSQL lane
   (area 5), including GitHub, Linear, Lark, and Microsoft Teams reply delivery. The matrix found and fixed one bug: a peer killed mid-call surfaced as gRPC `Unknown`
   ("transport error"), which the Worker Host and the Gateway's reply delivery treated as permanent.
   The host exited and left its Task running until the lease expired as uncertain, and the whole
   Gateway process exited from its Slack delivery loop. Both now treat an interrupted transport as retryable, and the
   Gateway reports an interrupted Control Plane call as `Unavailable`. Power loss is not
   simulated, and cannot be here: it needs a fault-injecting file system or block device under
   Linux root, and no portable test can observe an `fsync`. The settings that decide it are
   guarded instead (a pragma check that SQLite opens with `synchronous = FULL`, and the durable
   PostgreSQL lane); on macOS SQLite's `fullfsync` stays off, as in TypeScript.
